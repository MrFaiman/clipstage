# Architecture & implementation boundaries

## The first vertical slice

```text
Kick OAuth (authorization code + PKCE)
             │
             ▼
        NestJS API ───────── PostgreSQL / Prisma
             ▲                  │ users, identities, sessions
             │                  │ workspaces, memberships, invites
Next workspace                  │ devices, clips, edit decisions
             │                  │
             └──── signed GET ──┼──── private S3
                                ▲          ▲
OBS native dock ── initiate ── Nest        │
       │                                  │
       └──────── presigned PUT ───────────┘
       └──────── complete / verify ── Nest ──► INBOX
                                               │
                              editors see it on next 5s refresh
```

### Boundaries

- **Next** renders authenticated initial workspace data on the server; independent member/clip reads run in parallel. Interactive panels are client components. The upload and editor dialogs load dynamically. SWR owns server reads; Zustand owns only UI search/filter/view/navigation preferences.
- **Nest** is the authority for identity, membership, roles, upload ownership, and review permissions. Device credentials are accepted only by the initiate/complete endpoints, never by general workspace/clip reads.
- **S3** holds source files. Application servers never buffer video uploads or proxy playback. Object keys are generated by the server, not by clients.
- **PostgreSQL** stores metadata and non-destructive edit decisions. The original media never changes when an editor changes trim points.
- **OBS** owns local capture. C++ is necessary for its native module ABI; Qt handles the dock and asynchronous networking. No TypeScript runtime is embedded in OBS.

## Domain and tenancy

A `User` can own multiple `OAuthAccount` identities and belong to multiple `Workspace`s via `Membership`. A workspace has one owner at creation; there is no owner-transfer workflow yet. Members with `EDITOR` access can read, upload, assign, update briefs/trim decisions, and send clips for review. Only owners invite/remove editors, manage OBS devices, or approve clips.

Every clip, member, and device operation checks workspace membership. A device is additionally restricted to its workspace and can finalize only clips it initiated. A browser uploader can finalize its own uploads. DTOs never return object keys, token hashes, encrypted provider credentials, or raw device tokens except the one-time device-creation response.

Owners invite an editor by Kick email or Kick profile name. Clipstage does not send email and cannot search Kick's directory. A matching Kick account already stored here becomes an editor immediately. Otherwise the invite is kept for seven days and claimed inside the Kick sign-in transaction when that email or name appears. Several accounts with the same name must be invited by email. An existing member cannot be invited again. Identity linking still uses `(provider, providerUserId)` and never merges users by email.

## Authentication

1. `GET /auth/kick` generates state and a PKCE verifier. The attempt is stored with a ten-minute expiry and bound to an HttpOnly browser cookie.
2. Callback validates the matching state cookie and atomically consumes the attempt before exchanging its code.
3. The official `https://id.kick.com/oauth/token` exchange is followed by `https://api.kick.com/public/v1/users` with `user:read` scope.
4. Identity lookup uses `(provider, providerUserId)`, **never email**. A flow started while signed in links an additional identity only if that identity doesn't already belong to someone else. Linking requires the same session user at callback time.
5. Tokens are AES-256-GCM encrypted at rest using the 32-byte `TOKEN_ENCRYPTION_KEY`. Losing the key makes stored provider tokens unrecoverable; keep it outside the database and back it up securely.
6. Session tokens are random 256-bit values, hashed in PostgreSQL, and stored in host-only HttpOnly/SameSite=Lax cookies. Production uses the Secure `__Host-` prefix. Sessions expire after 30 days and rotate on successful OAuth.
7. Cookie-authenticated mutations require the exact `WEB_ORIGIN`. API requests from OBS use explicitly scoped bearer authentication instead.

Provider tokens are currently used for identity connection at login, **not** ongoing live-status polling or platform clip creation. Refresh-token rotation, remote disconnect/revocation, account settings, and Twitch/Google adapters remain follow-up work. Future Google integration must use Google's verified `sub` identifier, not its mutable email address.

### Deployment topology matters

The API's host-only cookie must also reach Next's server loader. Put both behind the same public hostname; route `/v1` to Nest. Different local ports on `localhost` work because cookies aren't port-scoped. Unrelated hosts or `app.example.com` / `api.example.com` don't work with this host-only SSR design. Configuration rejects different hostnames rather than silently failing authentication.

For example:

```dotenv
NODE_ENV=production
WEB_ORIGIN=https://clipstage.example.com
API_ORIGIN=https://clipstage.example.com
NEXT_PUBLIC_API_URL=https://clipstage.example.com/v1
API_INTERNAL_URL=http://api:4000/v1
KICK_REDIRECT_URI=https://clipstage.example.com/v1/auth/kick/callback
NEXT_PUBLIC_DEMO_MODE=false
```

TLS terminates at your proxy/load balancer. Next must have internal network access to Nest. Don't rewrite its `/v1` prefix away. Configure trusted proxy addresses and shared rate limiting before scaling; the current Nest limiter is in-memory and sees proxy addresses unless explicitly configured for your deployment topology.

## Upload protocol and correctness

1. Client generates a stable `clientUploadId` UUID and submits title, brief, filename, MIME type, declared byte count, and optional duration.
2. API creates an `UPLOADING` row and a server-owned key under `sources/:workspaceId/`. `(workspaceId, clientUploadId)` is unique. A retry returns the same clip; a different uploader or changed file metadata cannot take over the ID.
3. API returns a 15-minute presigned PUT with mandatory `Content-Type` and **`If-None-Match: *`** headers. The conditional header is cryptographically signed, so a client cannot remove it to overwrite an existing source. This also prevents replay of an upload ticket from silently modifying already-approved footage.
4. Browser/OBS streams bytes straight to the bucket. No app cookie/device bearer token goes to S3.
5. A retried PUT can return 412 if a previous attempt succeeded. The client continues to completion, where Nest checks the actual stored byte count and MIME type with `HEAD`.
6. Only after verification does a conditional update change `UPLOADING` to `INBOX` and increment its version. Repeated completion is idempotent and never resets later editing/approval status.

The maximum source size is 2 GiB; `MAX_UPLOAD_BYTES` can lower it. This is a single-PUT protocol, not a multipart/resumable protocol. A failed verification leaves the clip pending and its source immutable; start a new upload ID for a changed/corrupt file. Cleanup of abandoned uploads is not yet scheduled.

`HEAD` checks metadata, **not the actual video container or codec**. A real media worker must probe and validate untrusted files, obtain authoritative duration, generate browser proxies/thumbnails, and enforce resource limits. Client-supplied duration is only a UI hint. Future FFmpeg jobs must use bounded arguments and sandboxing, never shell-interpolated filenames/briefs.

Source/download URLs are signed for one hour. Membership removal stops new URLs, but already issued URLs can remain valid until they expire. Device revocation stops API access immediately, but an existing PUT ticket can remain usable for its remaining 15 minutes. The revoked device cannot finalize that upload. For tighter revocation requirements, shorten TTLs or use an authorization-aware media gateway.

## Editing workflow

```text
UPLOADING → INBOX → EDITING → IN_REVIEW → APPROVED
                                      owner-only ┘
APPROVED → EDITING (explicitly reopen before changing content)
```

`INBOX`, `EDITING`, and `IN_REVIEW` are flexible workflow labels, not a rigid sequential transition engine. Pending uploads cannot be edited. Approved clips cannot be silently modified; reopening to `EDITING` is required.

Every edit includes the version seen by the editor. Prisma updates only a matching `(id, workspaceId, version)` and increments it. A stale save returns **409**, rather than overwriting another collaborator's changes. Close/reopen the dialog to reload after a conflict. There is no automatic merge, audit history, or collaborative text editing yet.

VideoFlow edits the source in a client-only timeline. The complete VideoJSON document (up to 1 MiB) is persisted in `Clip.project`, including tracks, text, effects, and trims. The first video layer's `sourceStart` and `sourceStart + sourceDuration` also populate the legacy trim fields in seconds. The API derives these fields from the project when provided. Library polls omit the project; the editing room fetches the latest document and version before initializing a stable editing snapshot.

The original source is persisted as `clipstage:source` and rebound to the current signed playback URL on open, including duplicated/nested layers. Additional local dropped media has ephemeral blob URLs and cannot be saved until replaced with durable URLs or removed. MP4 export uses VideoFlow's built-in local browser download: no export is uploaded and the source object is never replaced. Browser codec support, CORS, and memory limits apply. Original downloads remain available for unsupported source formats. Server-rendered exports are still future work.

The library refreshes its first page every five seconds and fetches older pages on demand. Search/status filters operate on loaded pages, and the UI labels that limitation. Older loaded pages aren't continuously refreshed. SSE/WebSocket notifications and server-side faceted search are future improvements.

## Native plugin lifecycle

The dock installs after OBS's frontend finishes loading. It listens for recording-stopped and replay-saved events, snapshots the current brief/title, and queues an upload. Capture uses OBS's standard recording/replay outputs; it does not alter the stream, read the stream key, or download video from Kick.

- One active upload, up to 20 waiting jobs; manual retry/skip after failures.
- A stable UUID survives retries **within that OBS session**.
- File size/mtime are checked before retry; moved/modified sources must be re-added.
- API/PUT requests don't follow redirects; TLS verification stays enabled.
- Queue and credentials are memory-only; restarting loses pending jobs. Sources stay on disk, and the dock can upload an existing file.
- Source splitting, persistent queue, OS keychain, installer signing, unattended backoff, progress events to the app, and automatic updates are not implemented.

Linux ARM64 compilation was validated with Ubuntu 24.04's OBS 30.0.2 / Qt 6.4.2. This is **not** validation of GUI behavior inside an OBS stream. Test actual recordings/replays, app shutdown, network interruptions, source formats, and each OS/architecture before distributing binaries.

## Production roadmap / release gates

1. **Provider and capture verification:** real Kick credentials + callback domains; OBS GUI smoke tests; macOS/Windows builds and code signing; tests for recording shutdown, replay buffer, and output formats.
2. **Media processing:** durable job queue, file probing, thumbnails, H.264 proxies, non-destructive edit revisions, server-rendered vertical exports, progress/retry state, checksums, malware/resource limits.
3. **Upload resilience:** multipart upload, durable native queue, OS-keychain pairing, exponential backoff, reconciliation, orphan cleanup, storage accounting/quotas, maximum request size enforcement at every boundary.
4. **Operations:** backups/restore drills, observability and request IDs, shared rate limiting with correct proxy trust, auth cleanup jobs, audit logs, token-key rotation, provider refresh/revoke, managed secrets, alerting, signed binaries.
5. **Security review:** least-privilege IAM, bucket public-access block, encryption at rest, constrained CORS (`infra/s3-cors.json`), CSP/nonces and media-src policy, edge limits, dependency scanning, privacy/retention/deletion controls, concurrent membership/assignment edge cases.
6. **Collaboration:** push updates, global filtering/pagination, comments, revision history, deliverable upload/approval, editor notifications, direct platform publishing only with additional explicit consent/scopes.
7. **More providers:** Twitch and YouTube adapters, separate channel identity from source capture, provider-specific reconnection and refresh handling. No platform API should become a dependency of an OBS upload.

## Verification

- Shared schemas and crypto/origin/config tests run without services.
- API integration tests start real Nest on port 4400, seed isolated users/sessions directly in the test database, and test permissions, immutable S3 PUTs, retries, edits, and invites.
- Live browser tests use those test-only seeded sessions to verify Next SSR cookies, browser CORS/direct PUT, source playback, and saved edits. There is **no dev-login endpoint or production auth bypass**.
- Playwright demo tests cover filters/search, views, local sample uploads, editing persistence within a tab, honest integration states, and mobile overflow/navigation.
- Native Docker compilation checks the C++ source separately from Bun builds.
- Unit/integration tests do not substitute for a real Kick consent round trip, actual OBS runtime tests, load testing, or a production security assessment.
